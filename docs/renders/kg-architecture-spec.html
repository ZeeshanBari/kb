1 · The decisions

Chosen, rejected, and why — for everything

Decision A — compute shape A modular monolith. Not lambdas, not microservices.
Chosen
One app process and one worker process (two systemd units), same box, same repo, meeting only in Postgres.
Rejected
Lambdas — serverless prices spiky traffic; ingestion is a steady drip. Cold starts on an always-polling system, the 15-minute cap kills nightly extraction batches, and every function still needs Postgres for its cursor — you'd buy the fragmentation and keep the database anyway. Microservices — network boundaries between modules owned by one small team is operational cost with zero isolation benefit. Kubernetes — the control plane would cost more than the entire system.
Why
A boundary earns a wire only when a different machine needs it (the mini). The escape hatch is already built: the worker is a separate process — moving it to a second box is a DATABASE_URL change.
Decision B — hosting Hetzner CX42 + Cloudflare R2. About CA$31 a month, all-in.
Chosen
Hetzner CX42 (8 vCPU · 16 GB · 160 GB NVMe — €16.40 ≈ CA$26/mo, Falkenstein) · R2 for blobs + backups (zero egress, ≈ CA$3) · Tailscale free tier for the mini link. ~100 ms from Toronto is irrelevant here — the model round-trip dominates every answer.
Rejected
AWS (EC2 + RDS + S3) — the same capability assembles to ≈ CA$210–280/mo; 8× for logos. Fly / Railway / Render — lovely DX at 2–3× per GB of RAM, and RAM is our binding constraint (vectors). Oracle's free ARM tier — genuinely free, but accounts get reclaimed without appeal; fine as a staging clone, never as the company's memory. The Mac mini as the server — CA$0, but a single disk under a desk on a residential uplink. Already ruled out. Managed Postgres (RDS/Neon/Supabase) — CA$30–85/mo to avoid running one process, and the thing that actually protects the data is the tested restore, which is our job either way.
Why
Price-per-GB-RAM is the metric that matters, and Hetzner wins it by 3–8×. If US/Canada data residency ever becomes a requirement, the same stack lifts onto a CPX-class box in Ashburn at a premium (US pricing rose in 2026) — a config decision, not an architecture one.
Decision C — one database Postgres does everything: rows, queue, search, vectors, graph, audit.
Chosen
Postgres 17 — relational tables · event log · job queue (pg-boss) · keyword search (tsvector) · embeddings (pgvector, halfvec) · the claim graph (one table + recursive CTE, ≤ 4 hops).
Rejected
Redis — a second thing to secure and back up, for under 100 jobs/minute. Elasticsearch — a JVM and 1 GB of heap for a corpus Postgres FTS handles comfortably. Neo4j — a second database with its own backup, migration, and consistency story, for a graph that is literally one table. SQS / EventBridge — the event log must be queryable with the data; joins are the point.
Why
Backup = one database + one bucket. The monthly restore drill therefore covers the entire system. Every infrastructure component you add is another thing that can fail silently while its monitor reads green.
Decision D — language & stack TypeScript end-to-end. No ORM. Schema as code.
Chosen
Node 22 + TypeScript everywhere · Fastify · raw pg driver with idempotent DDL applied at boot under an advisory lock (no migration framework) · Zod at every boundary · React + Vite UI · Slack Bolt in socket mode · Vitest. Python only on the mini: mlx-whisper and Docling.
Rejected
Python core — extraction here is LLM-API work, not local-NLP work, so Python's library edge doesn't apply; two toolchains for one team is pure tax. ORMs (Prisma/Drizzle) — a codegen layer that owns your migrations, when the schema-as-code pattern needs raw DDL and ~15 tables of SQL is the clearer contract. Go edge agent — a second language to save 30 MB of RAM on a 16 GB machine.
Why
One language means one test runner, one lint stack, one mental model — and the connector ecosystem (Bolt, googleapis) is first-party TypeScript.
Decision E — surface A web app plus the Slack bot. Not a desktop app.
Chosen
Responsive web app behind Google OIDC (workspace-domain allowlist) for browsing, review queues, and evidence links — plus the Slack bot, because answers should arrive where questions are asked. Socket mode means zero public ingress beyond HTTPS.
Rejected
Desktop app — signing, updates, per-OS builds, and no shareable evidence URLs, for a multi-user org tool. Native mobile — responsive web covers the read paths. CLI — comes free later; it's the same API.
Why
A company knowledge base is judged by "can I send a colleague a link to the evidence." Only the web does that.
Decision F — observability platform Self-observing in SQL + Sentry + a dead-man switch. Not Datadog.
Chosen
Health signals are SQL views over the event log, rendered by the in-app status page. Sentry free tier (5k events/mo) for exception grouping and release tagging — the one thing SQL can't do well. healthchecks.io free tier as the external dead-man — the one failure SQL can't see is the box dying. Total: CA$0.
Rejected
Datadog — even this two-process, one-host system starts at ≈ CA$65/mo (Infra Pro US$15 + APM US$31 per host) before logs (US$0.10/GB ingested + US$1.70 per million events indexed); small production stacks typically land in the low hundreds USD — 5–10× our entire infrastructure, with high-water-mark host billing on top. Deeper problem: Datadog watches hosts and traces, and our failure modes are domain facts — a stalled cursor, an extraction backlog, spend vs cap, backup age. Those are custom metrics you'd hand-write in either world; the only question is where they render. And it ships company message metadata to a third party, against the self-hosted premise. New Relic — same shape. Grafana Cloud free tier — real, but a second pane of glass duplicating what the status page reads from SQL. Self-hosted Prometheus + Grafana — two more services to babysit for about a dozen gauges.
Why
With one event log, health is queries. Buy only what queries can't do: exception grouping (Sentry) and an off-box heartbeat (healthchecks.io). Exit paths: GlitchTip self-hosts on the same box if we outgrow Sentry's free tier; Grafana Cloud can read the same SQL views through a Postgres datasource if we ever want time-series charts. Neither requires re-instrumenting anything.
Decision G — the graph engine Steal GraphRAG's ideas, not its pipeline.
Chosen
Our own thin layer on Postgres: the claim table (evidence-mandatory · time-bounded · contradiction-flagging · label-enforced) + recursive-CTE traversal for local questions + nightly community detection (graphology + Louvain, in-process TS) with one Sonnet-written summary per community, stored as derived docs — which is what answers global questions like "what are our recurring supplier risks."
Rejected
Microsoft GraphRAG (the library) — built to batch-index a static corpus with LLM extraction over everything (the cost its own successor, LazyGraphRAG, exists to undo), and it owns its storage artifacts (parquet/LanceDB), which cannot host our invariants: no evidence-mandatory column, no validity windows, no access labels, no contradiction queue. A Python pipeline bolted onto a TypeScript system, solving the part that isn't hard. LightRAG / LlamaIndex property-graph — same storage-ownership problem plus framework lock-in. Neo4j GraphRAG — a second database, already rejected in Decision C. Graphiti (Zep) — the closest existing thing to what we need (bi-temporal edges, incremental episodes), and we borrow its temporal model — but it requires Neo4j/FalkorDB and Python services.
Why
Every graph library wants to own the store, and the store is where our guarantees live. GraphRAG's two durable ideas — local vs global search and community reports — are ~500 lines of SQL plus one nightly pass over our own schema. The genuinely hard part is extraction quality, and no graph library solves that; the eval gate does.
Decision H — models Claude behind one gateway. Local models rejected — for now, and for a reason.
Chosen
Haiku for triage, Sonnet for extraction and answers, structured outputs via tool-use JSON schema validated by Zod; a pinned embedding model (text-embedding-3-small to start). Every call goes through one gateway module — retries, auth-failure detection, daily hard-cap, cost log, cache-stable prompts. Model names are config, not code.
Rejected
Local models on the mini (Ollama/Qwen) — free tokens, but extraction precision gates the entire graph: a model that misses the .80 precision gate poisons every answer downstream, and the mini becomes both bottleneck and single point of failure. Worth revisiting for triage only, where a wrong call costs one skipped message. LangChain / LlamaIndex as the calling layer — the gateway is ~300 lines we must fully control (budget stop, citations, cost accounting); frameworks abstract away exactly the parts we need to own. Multi-vendor from day one — the gateway makes swapping vendors a config change later; two accounts of complexity before the first golden-50 run is premature.
Why
The graph is only as good as its extractor. Pay for the best one, and control spend with the funnel (only ~5% of content reaches it) plus the gateway's hard cap — not by degrading the model.

The RAM budget is the extraction funnel Embedding everything (~2M chunks) would cost ~6 GB of RAM in vectors alone. Embedding only documents and triaged threads (~200k chunks, halfvec) costs ~0.6 GB. The same 5% funnel that controls model spend keeps the whole system on a CA$26 machine.

Security posture, briefly

  • Ingress: 443 only. Slack is outbound (socket mode); the mini link is Tailscale; SSH is key-only behind Tailscale.
  • Auth: Google OIDC, workspace-domain allowlist. Access labels enforced in the store's read path — an HR channel never leaks into #general answers.
  • Secrets: SOPS-age-encrypted env file in the repo; decrypted only on the box.
  • Backups: nightly base + streamed WAL to R2 — and a restore is only real when the monthly drill proves it.

3 · Inside the monolith

Six modules that never import each other

The map in section 0 shows the layering: surfaces call features, features meet only in the platform — the store and the event log. A sideways import between feature modules is a build error, enforced by lint.

Platform invariants — on every row, from day one

  • Label on every row; reads fail closed; a derived row inherits its most restrictive input.
  • Provenance — every mutation names the event that caused it (caused_by).
  • Idempotency keys on anything replayable — ON CONFLICT DO NOTHING is the whole retry story.
  • Shadow flag on anything that acts — computed and recorded ≠ performed.
  • Derived is disposable — versioned builders + event-watermarks; deleting a derived table is always safe.

5 · Answering

An agent loop with exactly three tools

The answer engine is a small, budgeted agent loop given metric.lookup, evidence.search, and graph.walk — nothing else. A citation validator sits after composition: any sentence that doesn't cite evidence returned in this session is regenerated once, then dropped.

Why this is as deterministic as an LLM system gets The number comes from versioned SQL — exact, forever. The evidence set comes from pinned, non-sampling retrieval — reproducible. The graph walk is a CTE — deterministic. Only the final prose varies, and the validator pins every sentence of it to evidence IDs. Test the inputs to the prose, and wording stops mattering.

6 · Testing

Fast lies caught by PR, slow lies caught nightly

  • Store tests run against real Postgres — a CI service container, zero database mocks. Mocked-DB tests pass while production breaks; these can't.
  • Cassettes — each connector records real API payloads once; CI replays them. A nightly live smoke against a test workspace catches upstream drift.
  • The extraction gate — an extractor version may only run in production after clearing precision ≥ .80 / recall ≥ .70 on 200 frozen, labeled spans. Change the prompt or the model, re-clear the gate.
  • Golden 50 — real questions with known evidence sets and exact expected numbers. CI asserts the retrieval sets and the numbers — never the wording.
  • Determinism check — same fixture, same extractor version, twice → byte-identical claims (content-hash IDs make this a plain equality).
  • The restore drill is a test — monthly, scripted: pull the R2 backup, restore to a scratch container, verify row counts and checksums. A backup that has never been restored does not exist.

8 · Build order

Five phases, each with an exit test

PhaseExit test — green in CI, not "mostly done"
1 · Platform + IngestSlack and Drive land raw and searchable; killing and restarting the worker loses nothing; a stalled cursor alarms within its SLA.
2 · Resolve + Measure"Who is X?" returns one record across Slack/email/phone; the first five metrics live in git and return exact numbers.
3 · RelateClaims with evidence spans flow into the review queue; the extraction gate is cleared; re-extraction is byte-identical.
4 · AnswerGolden-50 ≥ 90% evidence recall, 100% exact numbers; every sentence cited.
5 · ActOne week of shadow kanban rows verified correct — then the flag flips and the first real card cites its answer.
