Install & Portability

From nothing to a running, verified system in one sitting — and the deep answer to "would the architecture have to change?": the skeleton stays; only the skin changes. Four changes, three new ADRs, one credential manifest.

0 · The claim

The architecture was already installable — we just have to package it

Every hard decision we made turns out to be an installability decision in disguise. That is not luck; simple systems are portable systems.

1 · The flow

Six steps, and CI walks the identical path nightly

# the whole install, as typed
npx kb@latest init        # questions → deployment dir: kb.config.yaml · compose · env skeleton
kb provision              # Hetzner box + R2 bucket + DNS  (BYO box? skip — point config at your host)
kb deploy                 # ssh: docker → compose bundle → Caddy gets TLS
# browser: https://kb.example.com  → one-time admin URL → the wizard
kb doctor                 # full converge · every check green · recovery key confirmed

3 · What changes — three decisions

The skin, not the skeleton

ADR-0010 — packaging Ship as OCI images + a versioned Docker Compose bundle.
Chosen
Images for app and worker, pinned by digest, composed with postgres:17 and caddy; named volumes for data. The deployment directory is the instance; the images are the software. systemd's only job left: restart policies.
Rejected
Bare systemd for distribution — the host OS becomes part of the product surface ("works on 24.04, not 22.04"). Kubernetes/Helm — a control plane again. Nix — real reproducibility, tiny audience. deb/rpm — a build-matrix tax forever.
Why
Identical bytes everywhere; upgrade = new tag + converge; rollback = previous tag; CI tests the exact artifact users run; the home-server tier comes free. This changes packaging — processes, modules, and database are untouched.
ADR-0011 — secrets Wizard-entered, envelope-encrypted in Postgres. One recovery key.
Chosen
Secrets entered once in the wizard, validated live, stored AES-256-GCM envelope-encrypted in Postgres with rotation fallbacks (QM's proven pattern). The master key is shown once — the recovery key — and is the only thing kept outside the system. Backups therefore contain everything: a restore restores a working system, connections included.
Rejected
SOPS for end users — key-file custody pushed onto the least-equipped party (it stays for dev/CI). Vault — a service to run, unseal, and back up, for a dozen secrets. Plain .env — either excluded from backups (restores are broken systems) or included (plaintext secrets in backups). Cloud KMS — a vendor inside the sovereignty boundary.
Why
The restore drill only means something if what comes back works. Concentrating custody into one key makes the human's job exactly one thing.
ADR-0012 — the installer A converge CLI. Infra-as-code in spirit — Terraform rejected in practice.
Chosen
One CLI — kb — where install is the first run of the reconciler: every step is check → fix → verify. Idempotent by construction, --plan for diffs, --answers for non-interactive runs. Provisioning calls vendor APIs (hcloud, Cloudflare) inside the same loop. Install, upgrade, drift-repair, and restore: one engine, four starting states.
Rejected
Terraform / Pulumi — a state file to keep safe, a second toolchain, and a second definition of desired state that will drift from the reconciler's — for three resources (a box, a bucket, a DNS record). Ansible — idempotence by convention, not construction. A bash script — the predecessor's 100 KB installer is the cautionary tale. PaaS templates — 2–3× cost forever, sovereignty broken.
Why
We already must build a converge engine for drift and upgrades. Reusing it for install means one mental model and zero state files. Exit: if resources ever grow past a dozen, put Terraform behind the CLI.

Installable ≠ instantly knowledgeable — say it honestly The system installs in an afternoon. The company's truth — its metric definitions, its labels, its golden questions — is authored by humans over the first weeks. We ship starter packs (a default ontology, template metrics, a golden-questions scaffold) so day one isn't a blank page; but the knowledge is theirs, and no installer can automate that.
