Ship, Onboard, Repeat

When a real user can start, how features ship behind flags, one onboarding flow for everyone, both paths proven in CI every night — and the workshop rules for agentic pull requests.

1 · When is it ready for a production test?

Production isn't a later place — people arrive in rungs

The box is production from stage 1; there is never a separate launch day. What changes over time is who we let in — and each rung is simply an exit test from the agreed plan, plus a bake.

Stage 1 exit
Live, but empty
Real box, backups running, restore already proven. No users yet — nothing to see.
Stage 4 exit + bake
🧪 Search pilot — the first production test
2–5 real users log in with Google and search real Slack + Drive. Safe because: labels enforced (stage 2), identities resolved (stage 3), TLS + SSO (stage 4), and losing the box loses nothing (stage 1).
Stage 6 exit + bake
🧪 Answers pilot — the product moment
The same users may now ask. Safe because: golden-50 green, every sentence cited or dropped, spend hard-capped. "Why did sales drop in March?" is now a supported question.
Stage 8 exit
Actions for real
Kanban cards — only after one shadow week is verified correct, per the plan.
Stage 9 exit
Strangers
Other people, other boxes. The stranger test (≤ 60 min, unaided) is what earns this.
The bake rule Each widening waits for 7 consecutive green days on the status page — zero unacknowledged failures or unverifiables. And every pilot complaint becomes a golden question the same day, so the pilots themselves grow the test suite that guards the next rung.

2 · Adding features after that

A feature is a registry entry; the flag is a row

Every feature declares itself in one place — the registry, in code, versioned and reviewed like everything else. Merged code is dark until an install completes that feature's onboarding; the flag isn't a third-party service, it's a row in Postgres that onboarding flips.

// بسم الله الرحمن الرحيم — the registry: every feature, declared
{
  key: 'connector.slack',
  version: 2,                        // bump ⇒ existing installs re-onboard the delta only
  needs: ['platform.core'],
  creds: ['SLACK_BOT_TOKEN', 'SLACK_APP_TOKEN'],
  cards: [appCard, tokenCard, channelsCard],   // the SAME wizard cards, install or upgrade
  enableCheck: slackSocketConnected,           // tri-state — shared with the status page
}

-- the flag store: one row per feature per install
feature_state(feature_key PK, state, version_onboarded, onboarded_at, onboarded_by)
-- code asks isLive('connector.slack') — nothing else. Kill switch = state→'paused', audited.

3 · Your rule, made structural

One onboarding flow — because it's one function

"The onboarding flow for old users onto a new feature should be the same as for a new user." The design makes that impossible to violate: a fresh install is onboard( ) looped over the whole registry; an upgrade is the same onboard( ) looped over the diff. Not two similar flows — one function, two loops.

ConsequenceWhy it falls out for free
The wizard is not install-day softwareIt's the permanent onboarding engine; stage 9 assembles cards that stages 2–8 already built and battle-tested
"Everything done once and properly"Each card is a converge step: it verifies, then advances; re-running a completed card is a check, not a redo
No half-enabled featureslive requires every card done and the enable_check green — the same tri-state the status page shows
Updates inform, never surpriseNew feature ⇒ announced state ⇒ the user chooses when to walk the cards

4 · Both scenarios, proven nightly

Two lanes into one contract

Because both journeys go through the same wizard API, CI can drive both end-to-end — and both lanes must land on the same final assertion suite. If the flows ever diverge, a lane goes red. Your principle is enforced by the build, not by memory.

CadenceWhat runsWhere
Every PRUnit + real-Postgres integration + check-docs (minutes)GitHub Actions runner
NightlyLane A (fresh) + Lane B (upgrade), compose-on-runnerGitHub Actions runner
Weekly + before any releaseLane A on a real throwaway Hetzner box (the stage-9 install CI)Hetzner hourly (≈ CA$0.02/run)

Lane B needs a previous version to upgrade from, so it switches on at the first tagged release — end of stage 1 — and from then on always tests N−1 → N.

5 · The agentic workshop

Well-structured PRs, worktrees, and who merges

RuleMeaning
One PR, one concern≤ ~400 changed lines as a guideline; bigger work becomes a stack of small PRs, each green on its own
No RD, no branchEvery code PR names its RD; pure docs PRs are marked docs-only
Evidence in the bodyThe exit-test run pasted into the PR — green output, not a promise. Plus: docs touched, risk, rollback, out-of-scope
Docs travel in the same PRBehavior change without its doc change can't merge — check-docs is a required check
Conventional commitsfeat(vault): … · fix(ingest): … · docs(adr): … — the changelog writes itself
Branchess<stage>/<slug> for stage work · fix/<slug> · docs/<slug>; worktrees live at wt/<branch>
Approval is the mergeYour call, recorded: I push branches and open PRs; you review and approve; with CI green, auto-merge lands it — no second click. Branch protection requires both. I never merge without your approval

6 · What I need from you — once, ~4 minutes

A scoped key to the workshop

The file bridge can't complete git operations (documented in conventions), so I'll work from a clone in my workspace and push over HTTPS with a fine-grained token scoped to exactly two repos. You stay the owner; I get contents and PRs, nothing else on your account.

  1. Create two empty private repos at github.com/new — names kb and kb-deploy. No README, no license (I push full history as commit #1).
  2. Mint the token: GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate. Name kb-agent · expiry 90 days · Repository access: Only select repositories → kb, kb-deploy.
  3. Permissions (repository): Contents read/write · Pull requests read/write · Workflows read/write · Administration read/write (only so I can set branch protection — skip it and click protection yourself if you prefer) · Metadata is added automatically.
  4. Paste it in chat.
