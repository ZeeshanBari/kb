The Execution Plan

Everything we've designed, in the order it should be built — with the reasoning for the order, an exit test per stage, your critical-path items flagged early, and the machinery that keeps it all testable and maintained.

0 · How this order was chosen

Four sequencing principles

PrincipleWhat it means here
Deploy the skeleton first, then build inside itThe compose bundle, kb deploy, backups, and the status page go onto the real Hetzner box at stage 1 — before features. Every later stage then ships continuously into production instead of facing a big-bang deploy at the end, and backups protect real data from the first week there is any.
Vertical slices, not horizontal layersEach stage ends with something you can use: search that finds a Slack message, a metric that returns the right number, an answer with citations in Slack. Never a layer that only pays off three stages later.
Your time is the scarcest resource — batch and front-load itVendor-console work is batched into single sittings (all of Google in one stage), and the one long-lead human task — labeling 200 spans for the eval gate — starts at stage 2 so it's never the blocker at stage 5.
Observability before the thing it observesThe status page is stage 1, the golden-50 harness is born before answers ship, and each connector arrives with its cursor alarm — so nothing is ever running unwatched, even mid-build.
11 + 1
Eleven stages plus one parallel track (the mini). Sized S/M/L — no dates; a stage is done when its exit test is green, not when a week ends
5 gates
Every stage passes the same five: RD agreed → built → exit test green in CI → checker green → deployed. Then you sign off
4 🔑
Items only you can do, all flagged in advance: GitHub auth (now) · Google consoles (stage 4) · 200 labels (start stage 2) · Full Disk Access (mini track)

3 · Testable and maintained — the machinery, not the intention

Every stage lives and dies by the same five gates

The requirement doc — one page, per stage

Wheredocs/06-requirements/RD-<stage>-<name>.md — same repo, same checker, same front-matter
ContainsGoal (2 sentences) · in/out of scope · exit tests, written as the CI assertions they will become · risks · rollback
LifecycleProposed → agreed (you) → frozen. Scope change mid-stage = amend the RD first, then the code — never the reverse
RuleNo RD, no branch. The exit test is written before the feature, so "done" is defined before work begins

Why stage 1 is the plan's strongest opinion Most plans put deploy, backups, and install polish last — and then a system that worked on a laptop meets production for the first time at the end, with everything at stake. Putting the skeleton on the real box first means every stage after it ships to production the day it's done, the restore drill runs monthly against ever-more-real data, and stage 9 is an assembly of proven parts instead of a leap. If you push back anywhere, push here — but this one I'd defend hard.
